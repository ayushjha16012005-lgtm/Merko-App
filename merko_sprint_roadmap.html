P2
Authentication & RBAC
Complete auth system: registration with OTP, JWT access + refresh tokens, role-based access control, session management
Sprints 2–32 weeksDepends on P1
Features
Register with name, email, phone, password
Phone OTP verification (6-digit, 5-min TTL)
Login returning access + refresh tokens in httpOnly cookies
Refresh token rotation — old token invalidated on use
Forgot password via email OTP flow
Logout — revoke refresh token from Redis
RBAC middleware: CUSTOMER, ADMIN, SUPER_ADMIN
Admin login with TOTP (2FA) — phase 2b
API endpoints
POST/api/v1/auth/register
POST/api/v1/auth/otp/send
POST/api/v1/auth/otp/verify
POST/api/v1/auth/login
POST/api/v1/auth/refresh
POST/api/v1/auth/logout
POST/api/v1/auth/forgot-password
POST/api/v1/auth/reset-password
GET/api/v1/users/me
PATCH/api/v1/users/me
Frontend pages & components
/login — LoginForm, email + password, error states
/register — RegisterForm, multi-step (details → OTP)
/forgot-password — ForgotPasswordForm
/reset-password — ResetPasswordForm
OtpInput component — 6-digit auto-advance input
AuthGuard HOC — redirect unauthenticated users
UserMenu — avatar, name, logout in header
Validation rules
Email: valid format, max 255 chars, unique in DB
Phone: valid Indian mobile (10 digits, starts 6–9)
Password: min 8 chars, 1 uppercase, 1 number, max 72 chars
OTP: exactly 6 digits, numeric, expires 5 min
Max 3 OTP attempts → 15-min lockout in Redis
Rate limit: 5 requests/min on /auth/* endpoints
Security requirements
bcrypt cost factor 12 — never store plaintext passwords
JWT in httpOnly, Secure, SameSite=Strict cookies — never in localStorage or response body
Refresh tokens stored as SHA-256 hash in Redis — raw token never persisted
Token rotation: every refresh call invalidates previous refresh token
OTP delivery via Twilio SMS — never returned in API response
Timing-safe comparison for OTP verification (prevent timing attacks)
Acceptance criteria
Registration flow: user receives OTP SMS, verifies, and lands on home with valid session
Login sets httpOnly cookies — no token visible in JS or response JSON
Expired access token + valid refresh token → silent re-auth via interceptor without user action
After logout, refresh token is deleted from Redis — replay attack returns 401
ADMIN role can access /admin/* routes; CUSTOMER role returns 403
After 3 failed OTP attempts, account is locked for 15 minutes

Validation rules

Saved design can be reloaded and all fields are pre-populated correctly

P6
Payments
Razorpay integration with full webhook security, idempotency, retry logic, and refund management
Sprints 11–122 weeksDepends on P5
Features & database
payments table — razorpayOrderId, razorpayPaymentId, razorpaySignature, status, method, capturedAt
Razorpay order creation server-side with idempotency key
HMAC-SHA256 webhook signature verification on raw body
Events handled: payment.captured, payment.failed, refund.processed
Idempotency check: duplicate webhook → 200 no-op
Stock decrement with row-level lock on capture only
Refund initiation via admin panel → Razorpay API
API endpoints
POST/payments/create-order [auth]
POST/payments/verify [auth]
POST/payments/webhook [razorpay sig]
POST/payments/:id/refund [admin]
GET/payments/:orderId [auth]
Security requirements
Webhook endpoint uses raw body parser — JSON parser breaks HMAC signature verification
No card data stored anywhere — PCI-DSS scope = SAQ A only
Payment amount verified server-side against order total — no client-submitted amounts trusted
Idempotency key stored in Redis (TTL 24hr) — prevents double-charge on network retry
Razorpay key_secret stored in Railway secrets only — never in codebase or logs
Acceptance criteria
Successful UPI payment: order status transitions to PAYMENT_CONFIRMED within 5 seconds of capture
Replaying a captured webhook event does not create a duplicate order or double-decrement stock
Tampered webhook signature returns 400 — no order state change
Admin-initiated refund reaches REFUNDED status and triggers customer notification
Payment failure allows retry up to 3 times without creating a new order

Sprints 13–142 weeksDepends on P6

orders — orderNumber, status enum, subtotal, discount, shipping, total (all in paise), notes
order_items — orderId, variantId, quantity, unitPriceInPaise, customizationData (JSONB snapshot), previewUrl
Order status index: idx on (status, created_at DESC) for admin dashboard queries
Partition orders table by created_at month for long-term scale
API endpoints
POST/orders [auth]
GET/orders [auth] — paginated history
GET/orders/:id [auth]
POST/orders/:id/cancel [auth]

Frontend pages & components
/orders — order list with status filters and pagination

OrderItemCard — product image + customization summary

Order status lifecycle
PENDING → only payment events advance this
PAYMENT_CONFIRMED → via webhook capture only
IN_PRODUCTION → admin manual update
QUALITY_CHECK → admin manual update
SHIPPED → admin + tracking number required
DELIVERED → admin confirmation
CANCELLED / REFUNDED → triggers auto-refund job
Acceptance criteria
Order creation is atomic — cart cleared, order + items + payment record created in one Prisma transaction
Customer cannot cancel order once status is IN_PRODUCTION or later — UI hides and API returns 409
Cancellation before production triggers automatic Razorpay refund via Bull MQ job
Order history loads 20 items per page sorted by created_at DESC in under 200ms
Customization data (name, photo URL, options) visible in order detail — even for old orders after schema change

Sprints 18–192 weeksDepends on P7
Features & channels

In-app feed — notifications table, bell icon badge, mark-as-read

Retry strategy: 3 attempts with exponential back-off per channel
Dead letter queue — failed jobs logged for inspection
Database & API
notifications — userId, title, body, type, entityType, entityId, isRead, createdAt
GET/notifications [auth]
PATCH/notifications/:id/read [auth]

Order confirmation email delivered within 30 seconds of payment.captured webhook
WhatsApp order confirmation delivered to customer phone using approved Twilio template
Failed notification job is retried 3 times; persistent failure lands in dead-letter queue without crashing worker
In-app notification bell shows unread count badge; mark-all-read clears it
Notification worker failure does not block or roll back the triggering order update
P10
Design Preview Engine
Canvas-based live preview rendering customer data onto product templates, with PNG/PDF export for print-ready files
Sprints 20–212 weeksDepends on P4
Features
LivePreview canvas — renders template + field data in real time
Text injection — font, size, color, position from previewConfig
Image injection — uploaded photo placed at configured canvas area
Background/overlay support — product template image as base layer
Preview PNG snapshot saved to Cloudinary at order time
Admin: download print-ready PNG/PDF per order_item from admin panel
Debounced re-render on field input — max 200ms update latency
Components & implementation
LivePreview — HTML5 Canvas or Fabric.js component, renders template layers
PreviewEngine — stateless render function: (template, fields, values) → canvas
CanvasExporter — canvas.toBlob → Cloudinary upload → URL returned
PrintExporter — server-side: Puppeteer/Sharp pipeline (Bull MQ job)
Preview snapshot triggered at checkout — before cart cleared
Acceptance criteria
Text fields update on canvas within 200ms of last keystroke (debounced)
Uploaded customer photo renders within image bounding box — no overflow outside defined area
Preview PNG uploaded to Cloudinary at checkout — URL stored in order_items.previewUrl
Admin can download print-ready PNG from order detail page for any order_item with customization
Preview renders correctly across Chrome, Firefox, and Safari (cross-browser Canvas API)

SQL injection payloads in all text inputs return 400 or sanitized response — no DB errors
